# 共用城市：設計調整規劃（待討論）

狀態：草案，尚未決定，不是承諾。來源是 2026-11-25 對 `impl/22-shared-city` 做的「好不好玩」審查（只看程式與參數，沒有看實際畫面）。#22 的實作只驗證「玩家選址、城市代建」的循環成立；以下是循環之外、仍會影響回訪的問題。

## 審查看到的事實

| 項目 | 觀察 | 來源 |
|---|---|---|
| 切法不影響結果 | 同樣的 token 總量切成 1、10、20 段，庫存完全相同；`/new` 不再多出工地 | 收入是 token 總量的函數，餘數跨回合累積 |
| 內容用得太快 | 5 種建築合計 45 單位；實測 26 分鐘就進帳 138 單位，第 1 天即可全部蓋完，之後庫存只增不減 | 建築表與一天的進帳 |
| 資源失衡 | 木是唯一瓶頸；同樣蓋完目錄，鐵多出約 200%、石約 38% | 目錄需求 木135／石65／鐵15 |
| 建築沒有功能 | 唯一效果是揭開土地；哨站的揭開效率（約 4.8 格／木）嚴格勝過其他建築 | `rules.js` 建築表 |
| 土地不稀缺 | 起始 63 格、57 個民居合法位置；蓋到 7 棟仍剩 344 格可建，占用約 3.6% | 選址沒有取捨 |
| 回訪沒有回饋 | 沒有「自上次以來」的資訊，完工只有一次性提示，且只在下令的那個視窗出現 | 地圖只反映當前狀態 |
| 預設畫面 | 預設仍是舊的遠征指揮桌；共用城市在按鈕後面 | 缺陷 3 處理後自然消失 |
| 誘因 | 基本收入完全來自 token；成果加成與 diff 大小無關，拆小 commit 的效率遠高於誠實工作 | 與 `proposal.md` 的原則衝突：輸入不能用 usage 當計分項 |

## 五個調整方向

每項都是候選，討論時先回答「它要解決玩家的哪個時刻」。

### 1. 建築要有功能，也要有資源出口
- 問題時刻：五種都蓋完、庫存還有幾百木卻沒有下一步。
- 想法：給建築可感知的效果（例如民居提高庫存上限、市場把多餘的石鐵換成木、書庫改善工作收入），並讓同種建築有遞減或升級；哨站的揭開成本隨範圍遞增。
- 要先決定：效果是增加選擇，還是變成必須最佳化的數值？不要把它做回另一個帳務系統。

### 2. 預排與可反悔（已決定，見 [ADR 0003](adr/0003-construction-queue.md)）
- 問題時刻：庫存充足，卻只能等一棟工期結束才能指定下一棟；位置點錯就永遠錯。
- 已採用：建設佇列上限 3 項；指定位置不動庫存，排到隊首、材料備齊才付料開工；未開工的項目可取消，占地與名額交還。
- 待觀察：試玩時看 3 項夠不夠、排隊中的項目佔著地圖會不會卡住規劃。

### 3. 收入與成果加成的誘因
- 問題時刻：多燒 token、拆小 commit 能更快蓋出建築。
- 想法：收入加每回合或每日遞減；成果加成依新增內容量分級並設上限，或降低到不值得刻意製造。
- 約束：訊號仍須是真實可驗證的，不能反過來懲罰使用額度。

### 4. 回訪摘要與完工演出
- 問題時刻：隔天打開，看不出哪裡變了。
- 想法：進場顯示「你不在的期間：進帳多少、完工哪些、揭開多少」；完工在地圖上有短演出，庫存增加有可見的變化。完工提醒要在任何視窗打開時都能看到，不只下令的視窗。
- 不做：隨機村民、假事件；城市安靜就該看起來安靜。

### 5. 去 geek 化的介面文字
- 問題時刻：第一眼分不清這是遊戲還是儀表板。
- 想法：頂欄的 token 進度改成直覺的進度條或移除；座標與「N 格」只在開發模式顯示；工作來源細節收進進階。

## 真實畫面驗證時看到的問題（2026-11-25，隔離 herdr 視窗）

| 觀察 | 影響 |
|---|---|
| 2×2 的書庫被畫成四棟一樣的小屋，只有其中一格寫著名字 | 一棟多格建築看起來像四棟；選址有整棟預覽，完工後卻失去整體感 |
| 揭開的地形用藍、綠、棕、灰四色格子表示，沒有圖例；要點一格才知道是深水、疏林、碎石或峭壁 | 哨站揭開大片新地後，畫面像散落的色塊，看不出哪些能蓋 |
| 左欄仍有「行會人力（provider 回報）」的額度文字 | 與「不必理解 provider」的方向衝突，屬於方向 5 |
| 空狀態寫「先開一個互動的 agent session，讓本機的工作進帳」 | 第一眼就是工具語氣 |
| 完工後的畫面變化只有頂欄、庫存卡與地圖上的建築圖形；沒有演出。完工提示是否出現未驗證（截圖在完工 22 秒後，短暫提示已過期） | 方向 4 |
| 施工中點其他建築卡或地圖格，右欄維持在施工資訊、帳本不變（這次只核對了這兩項，沒有確認有無提示） | 符合一次一項；若沒有提示，玩家會不知道為什麼點了沒反應 |

同一次驗證確認了好的一面：預覽用紅色標出造成「不能放」的那一格，原因寫在右欄；缺料時卡片直接寫「還缺什麼」，材料齊了改成「材料已齊」。

## 已知限制（不處理）
- 單一 commit 若涉及極大量路徑，成果 claims 會超過帳本單段上限而阻斷載入。使用者判斷實務上不會發生，因此不處理；[INFERENCE] 門檻可能只在數千個路徑的量級，若出現大規模機械式重命名或誤 commit 生成物，會是第一個炸點。
- 跨回合的用量修正（來源已入帳後才抵達的修正）仍以先入帳的為準；只處理了同一回合內的修正。

## 五日試玩要量的東西
每日收工後從共用帳本的 journal 取當日進帳 token、成果筆數、預定／開工／完工筆數；另外手記開城市次數、停留時間、誤點次數、當天能否說出「城市哪裡變了」。

| 指標 | 目標 | 紅燈代表 |
|---|---|---|
| 第 1 天完成棟數 | 0～2 | 3 棟以上：節奏過快，先調參數 |
| 第 3 天庫存 ÷ 目錄 | 小於 1.5 倍 | 大於 3 倍：沒有出口，先做方向 1 |
| 一週主動開啟天數 | 至少 3 天 | 不足：回訪動機失敗 |
| 有庫存卻沒有目標的空轉 | 每日不到 1 次 | 超過：預排需求成立（方向 2） |
| 誤點預定地且想改 | 0 次 | 一次以上：取消功能是必要的 |
| 能否說出「今天哪裡變了」 | 5 天中至少 4 天 | 說不出：回饋層失敗（方向 4） |
| 主觀「明天還想開」 | 至少 3 天 | 不足：停止擴充內容，回頭改機制 |

判讀：只有「第 1 天 3 棟以上」與「第 3 天庫存 3 倍以上」同時成立，才是結構問題；加再多建築種類只會多撐一天，必須先做方向 1 與 3。

## 2026-11-26 複審（game-designer ＋ ui-ux-designer）

- 「第 1 天即可全部蓋完」不成立：一棟民居＝20 木 ÷ 每份 3 木 × 10k ≈ 66.7k token。今天 07:29–12:05 實際 219k token（21 份：木 63／石 42／鐵 21），只夠 2 棟完工、1 棟缺料。工作 8 小時約 38 份、5 棟，所以「第 1 天 3 棟」這個紅燈在目前收入下幾乎天天亮，該改量「單日進帳 ÷ 目錄」或重設門檻。

- 「一次一項」已被 ADR 0003 的佇列取代；佇列滿時畫面會寫原因（`main.js:494`），不是默默沒反應。

### 建議順序（待決定）

1. 修上面的文件與註解漂移（已完成，`efbd39fd14`），量測改成目標導向（見下）。
2. 建築效果與資源出口：方向已定案，見 [ADR 0004](adr/0004-economy-in-units.md)（人口、進帳時扣維護、產出依地形、時代；探勘第二步）與 [ADR 0005](adr/0005-zoning.md)（分區自動施工，手動佇列只放一次性建築與升時代）。數值待分區原型。
2a. 地形生成重做（使用者 2026-11-26 提出）：現行起始區外是逐格雜湊（`core/city-map.js` 的 `hashedTerrain`，水 6%／峭壁 5%／疏林 15%／碎石 10% 各自獨立擲骰），結果是散點、不成片：河流不連續、林地沒有林地的樣子，分區也劃不出整片的伐木區或採石區。方向二選一或並用：雜訊加平滑的地形演算法（成片的林、連續的河與山脊），或手繪的地形模組（湖、河谷、林帶、礦脈）依種子拼接。約束：同一格永遠同一地形（決定性、不依時間）、迷霧裡的地形不洩漏、已揭開與已蓋的格子不能因演算法改版而變（需要版本化或只套用在未揭開區）。分區的模擬結果對地形分布敏感，地形定案後要重跑。
2b. 地形生成做法（2026-11-26 定）：混合——演算法生成大尺度的成片地形，依種子蓋上手繪模組（河、湖與橋點、礦脈、林帶）。前提不變：同一格永遠同一地形、迷霧裡的地形不洩漏、已揭開的格子不因改版而變。道路與橋（[ADR 0006](adr/0006-roads.md)）要求連續的河與成片的資源地。
3. 介面三項：窄版單欄 fallback（先定最小寬度）、去工程詞、缺料旁寫取得方式。每項都用截圖＋view 斷言驗。
4. 回訪摘要（方向 4）與固定情境存檔一起做，否則截圖與試玩都量不到「城市哪裡變了」。

### 節奏怎麼量（ADR 0004 之後）

- 以「份」量，不以日量：一個目標花幾份、有庫存卻沒有可做的事持續幾份。
- 原本五日試玩表的「第 1 天幾棟」「第 3 天庫存 ÷ 目錄」作廢；回訪類指標（主動開啟天數、說得出哪裡變了、明天還想開）保留。
